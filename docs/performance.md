# 画像転送・配置の性能確認

## herdr remote経由での初期表示

2026-09-29、利用経路がGhosttyへ直接ではなく`herdr --remote`と分かった。
別PTYを挟む計測では表示が消えたため、ソースをコピーした計測用バイナリを端末に直接接続して確認した。
largeは画像の読み込み・比較が約11ms、画像の準備が約12ms、左右の送信完了が起動後約30msだった。
圧縮は有効で、左右それぞれ1003×627px、制御列を含む画像出力は合計約0.2MBだった。
この時刻はspotdiffから接続先TTYへの送信完了までで、herdrの中継と外側のGhosttyへの提示は含まない。

インストール済みherdr 0.9.1の公式ソースでは、[画像の取得](https://github.com/herdrdev/herdr/blob/v0.9.1/src/ghostty/mod.rs#L1935)に展開後の画素を使い、[外側への送信](https://github.com/herdrdev/herdr/blob/v0.9.1/src/kitty_graphics.rs#L768)は圧縮なしのbase64になる。
この寸法ではRGBA画素だけで左右合計5,031,048 B、外側へ送るbase64と制御列は約6.7MBになる計算で、spotdiffの圧縮後出力より大きい。
remote接続では転送量が増えるが、中継全体の実転送量と時間はまだ測れておらず、今回の約1.5秒の遅延の主因だったとは確認していない。

同じログで、起動直後に表示幅が122列から123列へ変化していた。
この変更では左右共通のラスタ寸法が変わらず、送信済み画像の再利用が可能と判断していた。
しかしRatatuiはリサイズ時に画面をクリアし、herdr内の[画面クリア処理](https://github.com/herdrdev/herdr/blob/v0.9.1/vendor/libghostty-vt/src/terminal/kitty/graphics_storage.zig#L1169)は表示中の画像も解放する。
その後に配置だけ再送しても、参照する画像が存在しない。

端末領域が変わった場合は、ラスタ寸法が同じでも送信済み画像を再利用せず、左右とも新しい画像を準備して送る。
領域を維持した移動では引き続き画像を再利用する。
描画内部で取得したサイズがループ先頭のサイズと異なった場合も、キャッシュを使った配置を送らず、次のループで画像を準備し直す。
PTYで同じラスタ寸法となる48列→49列のリサイズを再現し、旧実装で配置だけが送られる失敗を確認してから、修正後に左右両画像の再送を確認した。
修正後、実際のherdr remote経由でユーザーから初期表示が「一瞬」になったと報告を受けた。
長時間の表示安定性はまだ検証していないが、今回報告された初期表示の体感遅延は解消した。

Ghosttyで初回表示とキー操作後の更新が重いという報告を受けて、描画の準備時間と転送量を切り分けた。

従来は、表示領域全体のRGBAをbase64化して無圧縮で転送していた。200列×60行、1セル10×20pxの左右比較では、1回の更新で約11.4MBを送る。PNGの読み込み・比較はbasicで約2ms、largeで約16ms、表示画像の準備は約28msだった。

端末にKittyのzlib圧縮対応を問い合わせ、成功応答がある場合のみ圧縮して転送するよう変更した。拒否・応答なしの場合は無圧縮で送る。比較・サンプリングの処理は変えず、PTYで圧縮を展開した画素が無圧縮と一致することを確認する。

## 計測結果

2026-09-28、Linux、releaseビルド。ローカルフィクスチャのbasic（640×400）とlarge（2048×1280）を使用。転送量は画像制御列とplaceholderを含み、見出し等は除く。

| 画像・端末サイズ | 無圧縮 | 圧縮 | 削減率 |
| --- | ---: | ---: | ---: |
| basic・100列×30行 | 2,475,324 B | 103,080 B | 95.8% |
| basic・200列×60行 | 11,369,280 B | 621,427 B | 94.5% |
| large・100列×30行 | 2,475,324 B | 134,332 B | 94.6% |
| large・200列×60行 | 11,369,280 B | 713,818 B | 93.7% |

200列×60行のbasicを起動し、Tab→+→-と操作したPTYでは、画像送信の完了までが以下となった。同じ更新済みバイナリに対し、圧縮の成功応答を返す場合と返さない場合を比較した。

| 操作 | 無圧縮 | 圧縮 |
| --- | ---: | ---: |
| 起動 | 112ms | 57ms |
| Tab | 111ms | 56ms |
| + | 108ms | 54ms |
| - | 101ms | 56ms |

単発計測のため時刻の値にはばらつきがある。PTYはデータを読み取るだけで、GhosttyのGPU描画や実画面の応答時間を測ってはいない。上記の削減率はこのフィクスチャでの値であり、写真等の圧縮しにくい画像では異なる。圧縮にはCPU時間が必要だが、basicの画像準備は約29ms→25ms、largeでは約28ms→31msだった。

## 回帰確認

- 圧縮対応の成功応答を返した場合、実際の画像転送に`o=z`を使用する。
- 拒否・応答なしの場合、無圧縮に戻り、表示画像の画素が圧縮の場合と一致する。
- 圧縮あり・なしの両方で、ズーム、移動、モード切替、2回のリサイズ、終了を確認する。
- 実lazygitを使うPTYでも圧縮対応の応答を返し、4通りの起動・復帰を確認する。

問い合わせとzlibの形式は[Kitty Graphics Protocolの公式仕様](https://sw.kovidgoyal.net/kitty/graphics-protocol/#compression)に従う。Ghostty 1.3.1の[画像読み込み実装](https://github.com/ghostty-org/ghostty/blob/v1.3.1/src/terminal/kitty/graphics_image.zig)にもzlib展開がある。

## 圧縮後も残った遅延への対応

圧縮後もGhosttyでは遅いとの報告があった。転送量の削減だけでは端末内の処理時間を説明できないため、Ghostty 1.3.1の描画処理を確認した。

従来の`U=1`とUnicode placeholdersによる配置では、Ghosttyが毎フレームKittyの配置状態を再構築し、画面内のplaceholderを走査する。[Ghosttyの配置更新実装](https://github.com/ghostty-org/ghostty/blob/v1.3.1/src/renderer/image.zig#L213-L324)にこの条件分岐がある。これが今回の実画面での遅さに寄与していると推測し、全画面ビューアの固定した画像領域では通常のKitty配置を使うよう変更した。文字セルにplaceholderを並べず、カーソル位置を指定して`a=T,c=…,r=…,C=1`で配置する。画像内容と圧縮の問い合わせは維持する。

合わせて次を変更した。

- 画像の準備中は直前の画面を残し、画像の削除・UI更新・新しい画像の配置をSynchronized Output内で行う。[Ghostty公式の推奨](https://ghostty.org/docs/help/synchronized-output)に従い、更新途中の画面を表示させない。エラーとpanicでも同期更新モードを解除する。
- 変更がないときは画面を再描画しない。
- ワーカーの完了を待つ間だけ入力pollを4msにし、画像の完成後に最大50ms待っていた遅延を減らす。
- 画像の表示寸法が同じリサイズでも、枠の位置が変わると配置を更新する。

同じ200列×60行のbasicのPTY計測では、圧縮時の起動・Tab・+・-の送信完了までが約58・55・53・56msから、約36・31・31・28msに短縮した。通常配置だけを先に試した段階では約57・53・53・53msで、PTYが測る送信完了時間への効果は小さかった。端末内のplaceholder走査を省く効果はこの計測には含まれない。

PTYで直接配置の座標・表示寸法・カーソル移動抑制、placeholder不使用、同期更新内での画像送信、待機中の再描画停止、エラー・panic時の同期解除を確認する。圧縮あり・なしのズーム・移動・モード切替・リサイズ、およびlazygitへの復帰も引き続き確認する。

上記はPTYでの計測で、GPU描画時間と実画面の体感は含まない。PTY計測をGhosttyでの応答時間として扱わない。

## 比較キャンバス外の余白を転送しない

操作の反応は速くなった一方、basicの初回表示が3〜5秒かかり、変更前しか表示されなくなったという報告があった。起動は`.superpowers/fixtures/compare.sh basic`で、releaseバイナリを使っている。

画面接続を指定し、Ghostty 1.3.1を実際に起動して端末処理の完了を測った。84行×174列、1セル14×32pxでは、640×400pxのbasicに対して従来は1190×2496pxの画像を左右それぞれ生成していた。比較キャンバス外の市松模様までラスタライズ・転送・テクスチャ化していたため、小さい画像でも処理量が端末の広さに比例していた。

表示画像を「表示領域と、現在の倍率・位置で見える比較キャンバスの共通部分」に限定した。basicの等倍では左右とも640×400pxになり、処理画素数が約91.4%減る。セル単位の`c,r`による拡大は行わず、生成した画像を実ピクセル寸法で直接配置する。比較キャンバス外は端末背景とし、透過部分・サイズ違い・差分強調の内容は維持する。

最終計測では、実Ghosttyの端末処理完了までが初回約16ms、Tab約6ms、2倍ズーム約25ms、等倍へ戻す操作約6msだった。計測時に限りKittyの成功応答を取得し、初回の左右両画像および以後の3更新すべてに`OK`を受け取った。製品は従来どおり`q=2`で端末への応答を抑制する。

同じ条件で余白ありの実装を検証用バイナリに再構成して比較した。起動から4表示を通した転送量は約6.72MBから約0.18MBになった。以前のPTYだけの結果よりも端末内のデコード・配置処理を含むが、GPUでの提示時間は含まない。

| 操作 | 余白あり | 比較キャンバス内のみ |
| --- | ---: | ---: |
| 初回 | 291ms | 16ms |
| Tab | 308ms | 6ms |
| + | 210ms | 25ms |
| - | 246ms | 6ms |

端末処理完了は、同期更新の終了後に送った`CSI 5 n`への応答で測る。独立した制御端末を持つPTYでspotdiffを起動し、実Ghosttyとのデータを中継する。計測専用のKitty応答は中継側で回収してキー入力へ渡さない。単発計測で、GPUのフレーム提示完了やユーザーが見た3〜5秒の再現確認にはならない。画面取得では有効な画像表示を確認できなかった。その後、ユーザーが同じ起動コマンドで左右両画像の表示と描画速度の改善を確認した。

回帰テストでは3×1pxのキャンバスを2倍にした場合に6×2pxだけを転送することと、展開した画素が期待する強調色・nearest neighborと一致することを確認する。小さい画像をペイン全体へ引き伸ばさないこと、圧縮・無圧縮で同じ画素になること、両画像の配置座標も確認する。

## ズーム後のhjkl移動

2026-09-29、同じGhosttyの84行×174列、1セル14×32px、release版でbasicを8倍にズームして確認した。従来は移動のたびに左右の1190×2496pxを生成・圧縮・転送しており、画像生成だけで約78ms、端末処理完了までは約122〜129msかかっていた。

表示領域の周囲に最大8セル分の画素を含め、端末に送った画像を再利用するよう変更した。保持範囲内の移動では、同じ画像ID・配置IDに対して `a=p,x=…,y=…,w=…,h=…,C=1` を送り、切り出す場所だけを変更する。[Kittyの公式仕様](https://sw.kovidgoyal.net/kitty/graphics-protocol/#display-images-on-screen)の配置置換と切り出しを使い、倍率の処理とnearest neighborは引き続きアプリ側で行う。ペインの外に余分な画素を表示しない。

ズーム、モード切替、表示寸法が変わるリサイズ、保持範囲外への移動では画像を作り直す。周囲の画素を含めた画像は1枚64 MiBまでとし、それを超える表示領域では周囲を保持しない。初回フィットでは画像全体が見えているため余分な画素を追加しない。ズーム時には周囲の画素を準備する分だけ負荷が増える。

画像生成中の連続入力にも対応した。未送信画像のIDは処理の完了まで保持し、古い要求で準備した画像でも最新の表示領域を正確に切り出せる場合は、配置を最新の入力に合わせてから送る。倍率・モード・領域・セル寸法が違う結果や、範囲外の結果は採用しない。古いエラーも引き続き無視する。

| 操作 | 修正前 | 保持範囲内の修正後 |
| --- | ---: | ---: |
| l | 122ms | 14ms |
| j | 127ms | 0.5ms |
| l（2回目） | 129ms | 0.4ms |
| j（2回目） | 122ms | 0.3ms |
| h | 122ms | 0.3ms |
| k | 128ms | 0.3ms |

左右両画像と6回の移動すべてに実Ghosttyから成功応答を得た。30ms間隔で30回 `l` を送る約0.9秒の連続入力では、修正前は入力中の画像更新が0回、最終版では19回だった。保持範囲を越える際の画像生成待ちは残る。この計測も同期更新後の端末応答までであり、GPUのフレーム提示完了を表すものではない。

回帰テストでは、移動中の画素転送の省略、切り出し位置、縮小・等倍・拡大時の画素一致、透過部分・左右比較・差分強調を確認する。準備済みの未送信画像を最新の移動へ合わせる場合、倍率・領域・セル寸法の変更で再利用できない場合、保持範囲外への往復での再送と所有する画像の削除も確認する。

レビューで、倍率5/3・6回の右移動において整数境界の丸め誤差で元画像の参照列が1pxずれるケースを確認した。サンプリングを画面上のピクセル座標で揃え、整数境界付近の浮動小数点誤差を除くよう修正した。元画像309列目を308列目として描画していた回帰をテストで確認し、修正後は保持画像と新規描画が一致する。

独立レビューの追加検証でも、7種類の倍率・非ゼロ原点・小数原点・前後左右の移動・3表示内容を含む417ケースで、保持画像の切り出しと新規描画の全画素が一致した。Rust 43テスト、端末PTY 10テスト、実lazygitの4シナリオ、fmt、Clippyを最終版で確認した。
